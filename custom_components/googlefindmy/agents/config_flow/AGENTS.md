# custom_components/googlefindmy/agents/config_flow/AGENTS.md

## Scope

Runtime + config flow guidance for every module under `custom_components/googlefindmy/`. Apply these instructions whenever
flows, service schemas, or reconfigure hooks are updated.

## Config flow registration expectations

* Keep `ConfigFlow.domain` explicitly declared in `config_flow.py`. This guards against future upstream changes that might stop injecting the attribute via metaclass magic.
* Never hand-register the flow through `config_entries.HANDLERS` unless Home Assistant drops automatic registration. If a regression forces a manual fallback, document the affected core versions, link the upstream issue, and add a TODO describing when to remove the workaround.
* Tests under `tests/test_config_flow_registration.py` cover both the domain attribute and automatic handler registration. Update them whenever the runtime behavior changes so the expectations stay enforced.
* Reference the Home Assistant developer docs on [config flow registries and handlers](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/#config-flow-handler-registration) when validating upstream behavior; keep this section aligned with any future changes noted there.
* When config flows iterate existing entries, guard optional Home Assistant attributes (for example, `ConfigEntry.source`) so discovery update stubs and other test doubles without those attributes keep working during local runs.
* Type-check the **frozen** entry attributes — `ConfigEntry.subentries`, `.data`, `.options` and a `ConfigSubentry.data` — against `collections.abc.Mapping`, never against `dict`. The core hands all of them out as `MappingProxyType`, so a `dict` guard is false for every real entry and true only for the mutable test doubles: it does not fail, it silently skips. `_gather_subentry_options` carried such a guard from 2025-10-27 until the fix; the effect was not an error message but a subentry selection reduced to the synthetic fallback option, so no assignment could persist while the suite stayed green (`tests/AGENTS.md` now asks entry doubles to expose the read-only shape for the same reason). The rule is deliberately scoped to those attributes and is **not** a blanket ban on `dict` guards: `data_entry_flow.FlowContext` is a `TypedDict` and therefore a real `dict` at runtime, which is why the `isinstance(context, dict)` guards in this module are correct and must stay — several of them mutate the context afterwards (`setdefault`, `pop`, item assignment), which a `Mapping` would not permit.

### Integration module imports

* When a config flow needs helpers from the integration package, import the module via `importlib.import_module(__package__ or DOMAIN)` rather than dereferencing `__package__` attributes directly. Home Assistant may start flows with a `None` package hint, and relying on `__init__` attributes can regress when the package layout changes. Centralize this pattern so helper lookups stay robust across runtime and test stubs.
* Prefer the shared lazy import helpers in `custom_components/googlefindmy/integration_modules.py` (`import_integration_package`, `import_integration_api_module`) so the API and package modules stay lazily loaded while keeping import targets centralized for future changes.

### Subentry alias handling

* Canonical service and tracker group keys now normalize legacy labels (for example, stray email-style identifiers) through the alias-aware subentry manager. When reconciling discovery or reconfigure payloads, prefer the canonical keys surfaced by the manager over any stored group labels so collisions realign to the correct service/tracker groups instead of amplifying drift.
* **The service and hub groups never carry `visible_device_ids`, and a device target is decided by a predicate, not by a bare key comparison.** Three production sites already write the invariant that way: `ServiceSubentryFlowHandler._visible_device_ids` and `HubSubentryFlowHandler._visible_device_ids` both return `()` unconditionally (unlike the `_BaseSubentryFlow` version they override, which reads the stored value), and `_async_sync_feature_subentries` builds its `service_payload` through `_build_subentry_payload` **without** the `visible_device_ids` argument while `tracker_payload` passes the stored ids. `tests/test_config_flow_subentry_sync.py` pins that result. **That omission also deletes, and the deletion is load-bearing rather than incidental.** Because the core replaces `data` wholesale, a payload without the key clears whatever the service group had stored -- and that is the repair which keeps a wrong assignment written by the pre-`e8114585` flow from becoming permanent, measured by `test_service_subentry_visibility_is_cleared_by_the_setup_roundtrip` on the manager side. Read together with `_accepts_device_assignment`, which refuses such a target, no *new* service assignment can be created, so everything the deletion removes is legacy residue. Anyone tempted to "preserve" it because the tracker branch preserves its own list should reach this sentence first: the two branches differ because the groups differ, and the tracker one is a device group. The reading side is a fourth, separately tracked enforcement (see below), and `ConfigEntrySubEntryManager.update_visible_device_ids` a fifth; a test asserts, it does not write. None of the three writers was an authoritative checkpoint, which is why `_async_assign_devices_to_subentry` could store device ids on the service group anyway. It now refuses such a target, and the three steps that assign devices (`async_step_visibility`, `async_step_repairs_move`, and the `_FIELD_REPAIR_FALLBACK` field of `async_step_repairs_delete`) build their choices from `_device_target_choice_map` instead of `_subentry_choice_map`. The two `_resolve_existing` implementations are deliberately not in that count: they are a separate axis, enumerated below, and they decide *which* subentry answers for a key rather than whether a group may hold devices at all.
  * **Scope of that checkpoint, stated because an earlier version of this paragraph overstated it.** `ConfigEntrySubEntryManager.update_visible_device_ids` (`__init__.py`) is a second writer of `visible_device_ids`, outside this module. It is no longer outside a guard: it now refuses to write to a subentry whose `subentry_type` is in `NON_DEVICE_SUBENTRY_TYPES`, the writing-side mirror of `_accepts_device_assignment`. That check reads the **resolved subentry**, not the key, so it holds whichever key a caller passes and whatever the alias table makes of it; today the only production caller already folds such subentries away, which makes this a second barrier rather than the only one, and that is the point, because a future caller would otherwise be unguarded. The alias table it resolves through no longer answers with a foreign group either: a **core key never aliases at all** (`core_tracking` and `service` each already name a group of their own, so a `service`-typed subentry still storing `core_tracking` can no longer redirect every tracker write onto itself), and a key that **two subentries of different canonical identities claim resolves to nothing** rather than to whichever the entry yielded first. The second half only works because a subentry whose canonical identity *is* its stored key registers that claim as well: a `hub`-typed subentry (`SUBENTRY_TYPE_HUB`, a type this integration really does create) canonicalises onto its own key and registers no redirection, so counting redirections alone would have left it uncontested and let a service twin capture the key. The ambiguity is remembered rather than merely dropped, so a third subentry cannot re-establish the mapping later in the same pass. Its caller in `coordinator/subentry.py::_refresh_subentry_index` no longer depends on the key axis either, see the canonicalisation note below. Measured, not read: both iteration orders of the service/tracker pair are pinned for the core key and for a legacy key, together with the `hub` axis and the reserved service key, in `tests/test_subentry_manager_registry_resolution.py`.
  * **The second writer inside this module, `_async_sync_feature_subentries`, now carries the type axis too.** Its `service_payload` omission (above) protects the *payload*, not the *target*, and its local `_resolve_existing` used to resolve on the stored `group_key` alone: the fallback scan matched it directly, the first branch trusted whatever the seeded context map held. A `service`- or `hub`-typed subentry that still stores `core_tracking` was therefore resolved *as* the tracker group and received `tracker_payload`, and the `if not tracker_visible and self._available_devices` fallback made that worse than a pass-through by filling a previously clean twin with every probed device id. The mirror direction lost data instead of adding it: a `tracker`-typed subentry storing the *service* key was resolved as the service group, received the id-less `service_payload`, and the update dropped the assignment it held. Both directions were measured against the real helper, and Codex reported the same defect independently. What replaced it, at `config_flow.py` `_canonical_core_key_of` and the module-level `_may_answer_for` beside it (module level rather than nested since `_BaseSubentryFlow._resolve_existing` became its second caller):
    * A candidate's **type** names the core key it may answer for, and **the two directions are not symmetric**. Every type in `NON_DEVICE_SUBENTRY_TYPES` folds onto `SERVICE_SUBENTRY_KEY` unconditionally, because that is the only key such a type may ever answer for. `SUBENTRY_TYPE_TRACKER` folds onto `TRACKER_SUBENTRY_KEY` **only when it stores `SERVICE_SUBENTRY_KEY`**, because several tracker groups with distinct keys are a supported shape that `coordinator/subentry.py` states and honours. A first version folded every tracker unconditionally and thereby adopted a legacy per-account group (`group_key = "owner@example.com"`), overwriting its key, title and identity: the axis meant to prevent a data defect producing one. A candidate whose type says nothing (absent, or outside that pair) and a tracker on its own key keep being decided by their stored key, which is the pre-existing convention of `_accepts_device_assignment` and the reason untyped doubles still resolve.
    * Inside this module the comparison against the set lives in **one** place, `_subentry_type_accepts_devices`, which both `_accepts_device_assignment` and `_canonical_core_key_of` call. Scoped to this module deliberately: `const.py` enumerates the consumers repo-wide (now five, since the feature sync joined them) and each of the others owns its own `in NON_DEVICE_SUBENTRY_TYPES` test. What the shared set prevents is a second *definition*, not a second reader.
    * The axis guards **both** branches, the seeded one and the fallback scan, because the migration path only ever reaches the second while the reconfigure path decides in the first. Each half has its own killing mutation, so neither is decorative.
    * An **exact stored-key match wins over a folded twin**. Where a real service subentry and a mis-keyed twin both answer for the service group, the exact match is taken and the twin is left alone, which avoids rewriting a stored identity nobody asked to change. That preference alone does **not** settle the order question, because two candidates can reach the *same* exit: two folded twins with no exact match, or a `service`- and a `hub`-typed subentry both storing the service key, a shape this module produces itself (`HubSubentryFlowHandler._group_key` is `SERVICE_SUBENTRY_KEY`). Measured, taking whichever came first turned an `AbortFlow` at `b75bea42` into a silent `async_remove_subentry` of the **canonical service group**, registry bindings included: exactly the trade `_claim_unique_id` exists to prevent, in the opposite direction. Both exits are therefore ranked, and the rank is substantive before it is stable: the type that *literally* owns the key (`_LITERAL_CORE_KEY_OWNER`) beats one that merely folds onto it, because the entity platforms match `subentry_type == "service"` literally; only among equals does the lowest `subentry_id` decide, where the value is arbitrary and stability is the whole requirement. The **seed is a tie-break inside that rank, not a precedence in front of it**: the seeder resolves through the runtime manager, which folds every tracker-typed subentry onto `TRACKER_SUBENTRY_KEY`, so it can name a subentry that carries the key in neither pool -- a hub beside the canonical service subentry, or a legacy per-account tracker group beside the canonical core group. Ranking such a seed ahead of the pool produced the same silent deletion one level up (measured: `AbortFlow` at `b75bea42`, canonical group swept afterwards). A seed therefore only decides among candidates that qualify for the key, and decides alone only when none does. No `-legacy` displacement is involved in any of this: `_claim_unique_id` only renames a subentry holding the *desired* unique id, and a losing twin on its own id holds neither.
    * The **reconfigure seeding** in `_reset_reconfigure_subentry_context` deliberately does *not* call this helper. Rewriting it was tried and reverted; the last bullet of this section records the measurement that decided it.
  * **Folding renames a `hub` the user created, and that is deliberate.** A `hub`-typed subentry is written with `service_payload`, the service title `Google Find Hub Service` and the service `unique_id` whatever key it stores, not only `core_tracking` but an email-style key or none at all, because the reading side (`coordinator/subentry.py`) folds exactly those three shapes the same way and pins all three, and the offering side (`_accepts_device_assignment`) refuses them all on the type axis; leaving the writing side on a third semantics is the drift the shared set forbids. Unlike a tracker, a hub on its own key is **not** a legitimate separate group: there is one service group, whereas several tracker groups with distinct keys are supported, and that asymmetry is the whole reason the two directions of the fold differ. The user-visible cost is the title, plus any `visible_device_ids` the subentry had accumulated, which are write-back residue by the same argument the reading side makes and are reclaimed by the unassigned-device merge rather than kept. The alternative considered and rejected was to leave such a subentry out of both core keys, which creates a third group beside it and raises the collision rate. **That paragraph describes the hub that *wins* the service slot, and the qualifier is not pedantry:** where a real `service`-typed subentry **storing the service key** sits beside it, the literal-owner rank hands the slot to that subentry and the hub is neither written nor renamed. The stored-key half of that condition is load-bearing and was overstated here once: the rank is compared *inside* `pool = exact or folded`, so a service subentry that only *folds* onto the key loses to a hub that stores it exactly, which `::test_an_exact_stored_key_match_beats_a_folded_literal_owner` pins. A hub that loses the slot is then not a cheaper outcome but a different one, a group of its own that keeps its title, its key and its stored ids, and the cleanup must leave it alone (see below); its `unique_id` is untouched by the rank, and where it happened to hold the *desired* id it was already displaced by `_claim_unique_id` before any of this. Reading the fold as unconditional is what made the delete path look safe. **One consequence, measured rather than argued:** where a lone `hub` is adopted into the service slot, the entry afterwards holds a `hub` and a `tracker` group and **no `service`-typed** subentry, so `known_ids_for_subentry_type(entry, SUBENTRY_TYPE_SERVICE)` is empty and `ensure_config_subentry_id` falls into its `if valid_ids` pass-through, i.e. it stops verifying rather than breaking. That is a shifted gap, not a new one: at `b75bea42` the same entry came out as a `hub` and a `service` group with **no `tracker`** type, and with the probed devices on the non-device twin. The fold trades an unverified platform lookup for a data defect; closing it means giving the hub the service type, which is a migration and belongs to `PLAN_GFMY_SUBENTRY_TYPE_MIGRATION`, not here; it is carried as `B12` in the register below, with the reason the core offers no in-place route.
  * **The axis turns an update into a create, so the create had to be made collision-proof.** `ConfigEntries.async_add_subentry` calls `_raise_if_subentry_unique_id_exists` unconditionally and `async_update_subentry` calls it whenever the `unique_id` actually changes; both raise `AbortFlow("already_configured")`. A twin that is left alone keeps `{entry_id}-core_tracking`, which is the very id the tracker group is then created under, and the reconfigure entry point has no `try` around the sync, so an unhandled collision would trade a data defect for a dead flow. `_claim_unique_id` displaces the **legacy holder** instead, never the canonical group, and searches until the substitute is free for the same reason `_unclaimed_fallback_key` does. That direction is not a preference: five sites outside this flow build their subentry definitions with `f"{entry_id}-{key}"` and reconcile against it (`__init__.py` at three, `coordinator/subentry.py` at two), so a core group carrying a derived id would collide with the runtime manager on the next sync and be resolved by its type-blind adoption path. Pinned by `tests/test_config_flow_subentry_sync.py::test_folding_a_twin_does_not_abort_on_the_unique_id_it_leaves_behind`, which asserts both halves: the canonical id on the tracker group and the `-legacy` suffix on the twin.
  * **Leaving a twin alone re-opened a delete path, so the cleanup needed the axis too.** `_async_cleanup_stale_subentries` classifies by stored `group_key` alone, and `ConfigEntries.async_remove_subentry` clears the device and entity registry bindings of whatever it removes. Before the resolver read `subentry_type`, a mis-keyed twin was always resolved by its stored key and therefore always landed in `context_map`, which kept it out of the stale list **by accident**. Once a real service subentry can win the exact-key match, that accident is gone: the twin is neither written nor seeded, and it matched `group_key in allowed_keys`. The cleanup now skips a subentry unless its type **literally owns** the key it stores (`_LITERAL_CORE_KEY_OWNER`), and that phrasing is the load-bearing part: the narrower rule "the type names a *different* core key" leaves a second victim behind. A `hub` writes `SERVICE_SUBENTRY_KEY` by design, so beside a real service subentry it is not mis-keyed at all, yet the literal-owner rank makes it the **deterministic** loser of the resolver, where taking whichever came first used to leave the outcome open. Classifying it by its stored key alone therefore traded one silent deletion for another, with the hub as the victim instead of the service group. An unknown key has no known owner and is skipped for the same reason: removal is irreversible, skipping is not. Only the literal owner can be a leftover copy of a core group; every other type sitting on the key is a group of its own. **An untyped subentry is deliberately not covered**, and that exclusion is a decision rather than an oversight: `_canonical_core_key_of` treats a missing type as "the stored key keeps deciding", so such a subentry *is* a candidate copy of the core group it stores, and sweeping stale legacy copies is the whole purpose of this pass. How reachable that shape is, is deliberately *not* claimed here: `ConfigSubentry.subentry_type` is a required keyword-only `str` in the installed core, so a missing type is not a shape the core's own dataclass produces, and the branch is defensive rather than a migration path. It is kept because widening the guard to "anything whose type does not literally own the key" would put every unknown or future type out of reach of the sweep, and the guard is what decides between skipping and an irreversible removal. What the diff does change for it is only *which* of two untyped siblings survives, not *whether* one dies, which is unchanged from `b75bea42`. Pinned by `::test_a_left_alone_twin_is_not_swept_up_as_a_stale_core_group` (mis-keyed twin), `::test_a_hub_losing_the_service_slot_is_not_swept_up_either` (same key, lost slot) and, in the opposite direction, `::test_a_genuinely_orphaned_core_group_is_still_removed`. The middle one is the only assurance the narrower rule fails, measured by restoring it. **The third non-owner combination is pinned too, and it is the one that needs a third subentry to exist at all:** a `tracker`-typed subentry storing `SERVICE_SUBENTRY_KEY`. Beside a real service subentry *alone* it is adopted into the tracker slot and re-keyed to `TRACKER_SUBENTRY_KEY`, so it never meets this pass on the service key; only once a canonical `tracker`/`TRACKER_SUBENTRY_KEY` sibling wins that slot does it stay behind on a key it does not own. Skipping it follows from the same ownership rule, and its assurance is a mutation of its own: narrowing the guard to `subentry_type == SUBENTRY_TYPE_HUB` kills `::test_a_tracker_parked_on_the_service_key_is_not_swept_up` in both entry paths and nothing else. **What survives is a parked subentry, not a clean one**, and the difference is named here rather than left to be rediscovered: the reading side (`coordinator/subentry.py::_refresh_subentry_index`) used to fold by *stored* key for every type outside `NON_DEVICE_SUBENTRY_TYPES`, so such a subentry kept being indexed under the service key and the branch a few lines down forced its visible, enabled and manager ids to `()`. PR #1230 closed that: a `tracker` storing the service key is now folded onto `TRACKER_SUBENTRY_KEY` on the reading side too, so it no longer reaches the service key at all (measured in both iteration orders, `::test_ap4_a_parked_tracker_reaches_exactly_one_group`). **What does *not* follow is a manager write-back, and saying it did was an overstatement in an earlier version of this sentence.** `manager_visible` is only filled for keys other than the service key, and the sole production caller of `ConfigEntrySubEntryManager.update_visible_device_ids` (`coordinator/subentry.py`, in the `if manager and manager_visible` loop) skips that key again before calling, so the type guard inside the manager is never even reached on this path. What used to follow was quieter and is the reason the follow-up existed: the ids the parked subentry stored kept counting into `stored_assigned_ids`, so the unassigned-device merge did not reclaim them, while the service branch had already emptied the metadata ids -- the devices ended up described by no group. That is fixed rather than merely described now. The reading side folds such a subentry onto the tracker key **and** exempts its ids from the in-memory assignment bookkeeping, exactly as the mis-keyed fold does, so the merge puts the devices in the tracker group. Only from the bookkeeping: the group keeps its allow-list, because an absent one would let it see every device rather than none. The two folds differ in what they are keyed on and that difference is load-bearing: this one is the **type** axis, so `test_a_device_moved_to_the_service_subentry_is_left_alone` is untouched -- the subentry there is `service`-typed on the canonical key, so a deliberate user move onto the service group is still not reclaimed. Measured, not argued: with a canonical tracker sibling present the fold alone left the devices in no group, because the parked subentry loses the core-key rank; exempting the ids from the assignment bookkeeping is what completes it. The read side now shares both the *rank* and this *fold* with this module. What it still does not share is the manager's unconditional tracker fold, so a legacy per-account tracker key stays a group of its own here. What the diff changes for this shape is *reachability*, not that behaviour: at `b75bea42` the three-way collision was resolved by removing one of the three, which one depending on `entry.subentries` iteration order, device and entity registry bindings included. A parked subentry is recoverable, a removed one is not.
  * **What this does not fix, named so nobody reads more into it.** Two open remainders and one gap that *is* closed here, kept in the list so the closure is not mistaken for a claim about the whole shape. First, a twin that is left alone keeps its stored `visible_device_ids`; the fix stops the supply, it does not clean up, and the reading side continues to exempt those ids from its in-memory assignment bookkeeping only. Second, `_BaseSubentryFlow._resolve_existing` had the same gap and it is now closed too: its fallback scan asks `_may_answer_for` beside the stored key, so the *handler* side no longer hands a `tracker`-typed subentry storing the service key to `HubSubentryFlowHandler` (nor a `hub`-typed twin on `core_tracking` to the tracker handler). The hand-over branch above the scan is deliberately left unguarded, because that object identifies the subentry the user opened and filtering it would make a mis-typed subentry unreconfigurable; that branch is unreachable today (`async_get_supported_subentry_types` returns `{}` unconditionally, so core never registers these handlers, and `async_step_hub` passes no `subentry`) and is left open so the asymmetry is right the day core does hand one over. What the closure does *not* do is reach a working create where the twin is refused: `ConfigSubentryFlow.async_create_entry` raises `ValueError("Source is None, expected user")` before `async_add_subentry` is called, because `async_step_hub` sets a context without `source`. That raise is **pre-existing** and reproduces on an entry holding no subentry at all, so the axis widened the inputs that reach the branch rather than creating the dead end; it is tracked as `U-28`, and the `unique_id` collision waiting behind it as `U-27`. Third, a **legacy per-account tracker group is still adopted on the reconfigure path when it stands alone**, and both halves of that sentence are measured rather than assumed. The adoption itself reproduces at `b75bea42`, i.e. before this axis existed, because `ConfigEntrySubEntryManager` keys every tracker-typed subentry under `TRACKER_SUBENTRY_KEY`, so `_reset_reconfigure_subentry_context` receives such a group already renamed and never reaches its own type branch. It stops where the **canonical core group sits beside it**: a seed only ranks among candidates that carry the key, and the legacy group is in neither pool, so the canonical group keeps the slot. That half is not cosmetic and was found late: while the seed still outranked the pool, this shape rewrote the legacy group onto the core key and then swept the canonical one, registry bindings included, where `b75bea42` raised `AbortFlow` and kept both. Pinned by `::test_a_seed_that_does_not_carry_the_key_yields_to_the_stored_match` over both insertion orders. Rewriting that branch was tried and reverted: it does not reach the defect and would let a legacy `hub` win the service slot ahead of a real service subentry depending on manager iteration order. The manager fold is where the defect lives, with its own blast radius (runtime index, manager adoption), and it is tracked as `B13` in the register below, owned by `PLAN_GFMY_SUBENTRY_TYPE_MIGRATION`. All three are left to their own change; `tests/test_config_flow_subentry_sync.py::test_a_legacy_tracker_group_on_its_own_key_is_left_alone` therefore pins the migration path alone and says why in its docstring.
  * **Register of the remainders this change carries rather than closes.** Every entry below names four things and is incomplete without all four: the **condition** under which the shape is reachable, the **consequence** a user or a later reader meets, the **date** it was carried, and the **follow-up plan** that owns it. Three of the four are the usual contract discipline; the fourth is here because a remainder whose owner is a plan that has already shipped reads as tracked while nothing tracks it, which is worse than no reference at all. None of these is a defect this change **introduces newly**, and the sharper wording matters because two entries have to defend themselves against the absolute version: for B12 and for U-28 the change shifts or widens the *reachable shape* of a pre-existing gap, and each says so in its own entry. None is a reason to widen this change either: each was measured, each is bounded below, and each is left where its blast radius can be tested on its own. **The register is complete for the remainders of this change and not for the file**: four further remainders share one root of their own -- a group holding ids nothing describes, and a missing allow-list read as "sees everything" -- and are carried together by `PLAN_GFMY_VISIBILITY_ASSIGNMENT_BOOKKEEPING`. That group was `U-25`, `U-26`, `U-30` and `U-31`; `U-26` is **closed** since the normalisation began keeping the empty set for every group (`ffde3fc6`), and `U-25` is **closed** since the branch that synthesises a missing tracker subentry began excluding what another group owns (`989e8634`), so the open set is `U-30`, `U-31` and, newly, `U-34` and `U-35`. Both closures name a commit *and* their pull request, #1235: this repository merges branches rather than squashing them, so the hashes survive, but the pull request is what a reader still finds if that practice changes. The same change also closed a **producer** of the fail-open direction that never had a `U-` name here because it lives in the runtime contract: the setup sync deleted every stored field its definition did not carry (`0ce87ae2`); it is described under "A definition is a partial description" in `agents/runtime_patterns/AGENTS.md`, together with the two further deletion sites of that change and the one deletion that is a repair rather than a defect. **`U-34`**, stated to the same four-part discipline as the entries below: *condition* -- **any** group that stores no `visible_device_ids` key at all, the default one included; *consequence* -- it is read as unrestricted and therefore sees every device, including those another group owns through a non-empty stored list, and the unassigned-device merge does **not** cushion this the way it cushions an empty stored list, because an absent key never restricts in the first place (`::test_ap3_a_stored_shape_decides_what_a_group_may_see[E2]` pins both readings side by side); *date* -- 2026-08-06, measured while closing `U-26`; *owner* -- `PLAN_GFMY_VISIBILITY_ASSIGNMENT_BOOKKEEPING`, which carries it deliberately rather than closing it here, because the question it raises is whether *unrestricted* should exclude foreign ownership, and that is decided where `allow_filter is None` is **read**, not where it is set. **`U-35`**, to the same discipline: *condition* -- any group whose stored list normalises to nothing, that is `[]` or a list of unusable entries, once a coordinator refresh has run; *consequence* -- the refresh writes a derived list back through `ConfigEntrySubEntryManager.update_visible_device_ids`, which levels the stored shape. For a non-tracker group the stored value becomes `[]`, so the count in `_record_allow_list_reinterpretation` reads `0` on every later emission and a migration artefact becomes indistinguishable from a deliberate emptying, which is precisely the distinction that record exists for. ### Optional `ConfigEntry` attributes in tests

Local discovery and reconfigure tests instantiate lightweight `ConfigEntry` doubles that frequently omit optional attributes Home Assistant adds at runtime.

* `source` — prefer `getattr(entry, "source", None)` before accessing the field so `async_step_discovery` continues to work with the stubs in `tests/test_config_flow_discovery.py`.
* `pref_disable_new_entities` / `pref_disable_polling` — guard these through `getattr(..., False)` when feature toggles depend on them, because flow helpers in the test suite never populate the preferences block.
* `state` — normalize through `getattr(entry, "state", None)` before checking reload eligibility; the discovery update fixtures only set `entry_id`, `data`, and sometimes `unique_id`.

Add similar guards whenever a new optional attribute becomes relevant so future config flow helpers remain compatible with the suite's minimal stubs.

* **Preserve parent-platform forwarding state across retries.** When a setup, reconfigure, or auth retry path short-circuits the normal flow, retain the `_gfm_parent_platforms_forwarded` flag on `entry.runtime_data` so unload handlers can skip subentry teardowns when parent platforms were never forwarded. This prevents `ValueError: Config entry was never loaded!` noise after partial setups.
* **Reconfigure context markers.** Home Assistant populates `flow.context["entry_id"]` when a reconfigure flow starts (for example via `config_entries.async_start_reconfigure`). Treat that value as authoritative when routing the user step so the flow stays bound to the existing entry instead of tripping duplicate-account guards. Inline comments should call out this guard relaxation to preserve the single-parent-entry rule for new setups while keeping reconfigure detours safe.
* **Manual token UI path disabled.** The `_AUTH_METHOD_INDIVIDUAL` choice in `STEP_USER_DATA_SCHEMA` remains commented out because the manual token + email path is broken. ## Service validation fallbacks

* When raising `ServiceValidationError`, always include both the translation metadata (`translation_domain`, `translation_key`, and `translation_placeholders`) **and** a sanitized `message` that reuses the same placeholders. This keeps UI translations working while ensuring Home Assistant surfaces a readable fallback when translations are unavailable.
* The fallback message reuses the placeholders except values that may carry an account e-mail (entry titles): Home Assistant logs `str(err)` for every caller of a failed action. Such a value stays out of the placeholders as well, because every caller with access to the action sees them; `no_active_entry` therefore passes only the two counts; no entry list placeholder exists.

## Config entry options persistence reminder

* Treat `ConfigEntry.options` as immutable during reconfigure flows. Build a new dictionary (for example, `existing_options = dict(entry.options or {})`) and pass it directly to `async_update_entry` instead of mutating `entry.options` in place. Home Assistant only persists option changes when it detects a new mapping, so keep the original object untouched until `async_update_entry` returns. See the [`async_step_reconfigure` options-copy pattern](../../config_flow.py#L2929-L2943) for a concrete implementation:

  ```python
  existing_options.update(options_payload)
  self.hass.config_entries.async_update_entry(
      entry_for_update,
      data=merged_data,
      options=existing_options,
  )
  ```

## Device ownership in flow code

The config flow binds the service device itself. Any such binding is an **ownership**
change, and from Home Assistant Core 2026.8 a device belongs to exactly one config
entry and exactly one config subentry. Do not pass `add_config_entry_id`,
`add_config_subentry_id`, `remove_config_entry_id` or `remove_config_subentry_id`
from flow code: on a modern core the first only arms a deferred move, and the third
*deletes* the device when the removed subentry is the one the device sits on and no
such move is armed.

Where to route it depends on what the flow has at hand. When the coordinator is
reachable, go through its ownership entry point. When it is not (the flow has a
coordinator-less fallback path that calls `dev_reg.async_update_device`
directly), call the pure planner `plan_device_ownership` from
`custom_components/googlefindmy/coordinator/helpers/registry.py` and run the
operations it returns through `execute_ownership_plan` in the same module;
neither needs `hass` nor a coordinator instance. Import that helper module inside
the function that uses it, never at module scope: the import runs
`coordinator/__init__.py`, which loads the full API graph, and the flow-only import
path must not depend on that graph ("Integration module imports" above). There are
two executors and that
is deliberate, because not every call site has a coordinator; what stays single
is the *translation*. What must
**not** happen is a third hand-written keyword translation in `config_flow.py`. One
used to live there, a `TypeError` retry that renamed `add_config_*` to `config_*`;
it was removed in AP-15, and its rename produced a keyword no supported core takes
(`async_update_device` has no bare `config_subentry_id` at tag 2025.9.1, 2026.8.0
or 2026.9.0). Do not restore it: an error message is not a signature, and the
planner reads the signature.
Background and deadlines: `docs/AI_DEPRECATIONS_GUIDE.md`, section VI.

## Subentry handler registration (HA 2026.x compatibility)

### `async_get_supported_subentry_types` MUST return empty dict

**Critical:** This method MUST return `{}` to hide unwanted UI buttons in the config entry panel.

**Why empty dict is required:**
- Returning handler classes causes HA to display "+ Add hub feature group" and "+ Add service feature group" buttons
- These manual subentry buttons should NOT be visible to users
- Subentries are provisioned **programmatically** by the integration coordinator, not manually

**Correct implementation:**
```python
@classmethod
@callback
def async_get_supported_subentry_types(
    cls,
    _config_entry: ConfigEntry,
) -> dict[str, type[ConfigSubentryFlow]]:
    """Return empty dict to hide subentry UI buttons."""
    return {}  # MUST be empty to hide manual add buttons
```

**Wrong implementation (exposes unwanted UI):**
```python
# DON'T DO THIS - exposes "Add hub/service feature group" buttons!
return {
    SUBENTRY_TYPE_HUB: HubSubentryFlowHandler,
    SUBENTRY_TYPE_SERVICE: ServiceSubentryFlowHandler,
}
```

### `async_step_hub` must instantiate handlers directly

Since `async_get_supported_subentry_types` returns empty, the "Add Hub" flow entry point (`async_step_hub`) must instantiate the handler class directly:

```python
async def async_step_hub(self, user_input=None):
    # Don't use async_get_supported_subentry_types - it returns {}
    # Instantiate the handler directly instead
    handler = HubSubentryFlowHandler(config_entry)
    setattr(handler, "hass", hass)
    setattr(handler, "context", {"entry_id": config_entry.entry_id})
    result = handler.async_step_user(user_input)
    return await self._async_resolve_flow_result(result)
```

### Lazy `config_entry` resolution for handler compatibility

Subentry handlers use a `config_entry` property with lazy resolution to support both direct instantiation and potential future HA flow manager usage:

```python
@property
def config_entry(self) -> ConfigEntry:
    if self._config_entry_cache is not None:
        return self._config_entry_cache

    # Fallback: try HA's _get_entry() method
    get_entry_method = getattr(self, "_get_entry", None)
    if callable(get_entry_method):
        entry = get_entry_method()
        if entry is not None:
            self._config_entry_cache = entry
            return entry

    raise RuntimeError("Cannot resolve config_entry")
```
