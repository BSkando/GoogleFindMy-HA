# custom_components/googlefindmy/agents/runtime_patterns/AGENTS.md

## Scope

Runtime contracts, platform forwarding rules, and HA lifecycle helper usage for every module under `custom_components/googlefindmy/`.

## Runtime integration patterns

* Collect runtime-contract reminders for integration touchpoints in this section so future contributors can find them without scanning unrelated guidance.
* View classes under `custom_components/googlefindmy/map_view.py` should expose constructors that accept `HomeAssistant` as the first argument. Register new views by instantiating them with the active `hass` instance (for example, `GoogleFindMyMapView(hass)`) instead of assigning `hass` after creation so the runtime contract stays consistent.
* **Service-to-coordinator propagation:** When a service handler invokes a coordinator method that returns a boolean (for example, play/stop sound helpers that suppress requests when push is unavailable), raise `ServiceValidationError` when the result is `False` so callers and UI surfaces receive an explicit failure instead of silent success logs.
* **Platform forwarding reminder:**
  * The parent `async_setup_entry` handles coordinator/bootstrap work and explicitly triggers platform setup for any new subentries by calling `_async_setup_new_subentries`. Home Assistant subentry flows do not automatically fan out to platforms.
  * Forward setups **once per platform set** via `_async_setup_new_subentries` by gathering the union of required platforms and calling `hass.config_entries.async_forward_entry_setups(parent_entry, platforms)` **without** `config_subentry_id` or other kwargs (see the interface snapshot in [`docs/CONFIG_SUBENTRIES_HANDBOOK.md`](../../../docs/CONFIG_SUBENTRIES_HANDBOOK.md#quick-ssot-probe-per-subentry-platform-forwarding)).
  * Immediately after forwarding, emit dispatcher signals for each subentry so platforms receive the full `ConfigSubentry` object and can attach entities per child.
  * When forwarding or unloading the **parent entry's** own platforms, continue passing a `tuple` of platform names to `hass.config_entries.async_forward_entry_setups`/`async_forward_entry_unload`. Home Assistant caches these iterables and expects immutability during parent-level fan-out.
  * Track whether parent platforms were actually forwarded on setup using `_gfm_parent_platforms_forwarded` in `RuntimeData` and skip unload calls when the flag is `False` to avoid `ValueError: Config entry was never loaded!` noise during retries.
  * Extend the same guard to subentry unload logic: only fan out unload calls (for example, tracker and service subentries) when `_gfm_parent_platforms_forwarded` is `True` so Home Assistant never attempts to tear down platforms that were never loaded.
  * Each platform must iterate the subentry coordinators stored on `entry.runtime_data` and add entities per child when signaled by the dispatcher. Deduplicate entities per subentry to avoid `_2`/`_3` suffix churn on reconnects or retries.
  * Leave a short inline comment explaining which pattern you chose whenever platform lists move between parent and subentry paths.
  * The legacy `RuntimeData.legacy_forwarded_platforms`/`legacy_forward_notice` tracking remains in the codebase for historical builds but should stay dormant on modern Home Assistant releases.
* Use the shared `_async_setup_new_subentries` helper whenever subentries are created (during parent setup **and** at runtime) so every child receives a dispatcher signal after the single forward pass.
* Once subentries exist, invoke `_async_setup_new_subentries` **without** `enforce_registration=True`. The registration delay loop is reserved for missing IDs; removing the flag prevents an infinite `ConfigEntryNotReady` retry cycle when Home Assistant is already finalizing the registry.
  * See [`docs/CONFIG_SUBENTRIES_HANDBOOK.md#automatic-retry-queue-for-unknownentry`](../../../docs/CONFIG_SUBENTRIES_HANDBOOK.md#automatic-retry-queue-for-unknownentry) for the bounded retry/backoff design that `_async_setup_new_subentries` enforces when `UnknownEntry` fires.
  * The retry queue stores its handles and per-subentry attempt counts on `entry.runtime_data` (for example, `RuntimeData.subentry_retry_handles` and `RuntimeData.subentry_retry_attempts`). Keep those runtime caches typed and cleaned up during unload so strict mypy runs continue to catch handle leaks or mismatched awaitables as the queue gains new states. After adjusting imports near these helpers, run `python -m ruff check --select I --fix` to keep the lint-driven sorting from masking future docstring or typing diffs.
* Home Assistant's subentry helpers (`async_add_subentry`, `async_update_subentry`, `async_remove_subentry`) may return a `ConfigSubentry`, a sentinel boolean/`None`, or an awaitable yielding one of those values. Always normalize results through the shared `_await_subentry_result` helper (or an equivalent `inspect.isawaitable` guard) so asynchronous responses update the manager cache correctly.
* Tracker device healing should clear any stray `config_subentry_id` links for the current entry before applying the expected tracker link so only the parent/child pair remains associated with a hub. Log the removed subentry IDs to aid debugging of multi-hub migrations and keep tests aligned with the coordinator helpers that enforce this cleanup. Add a short reminder near new healing helpers when they mutate registry links so future contributors retain the cleanup-and-log contract, and document the cleanup in related changes so future maintenance keeps the coordinator behavior in sync with the guidance here.
* **Hub-level name collision handling:**
  * Before creating or updating tracker devices, collect the existing device names linked to the hub and store them in a local set. Resolve each name with `async_get_device_by_identifier(identifier, config_entry_id)`, which takes **one** identifier tuple and the owning entry id, and not with `async_get_device({...})`. Reason: from Core 2026.8 identifiers are only unique *within* a config entry, so a set-based lookup can return a device owned by a different GoogleFindMy entry, and the winner depends on iteration order. `async_get_device` is deprecated with `breaks_in_ha_version="2027.8.0"` (`homeassistant/helpers/device_registry.py` at tag `2026.9.0`, line 1967). Fallback rule for cores below `2026.8.0`, which do not have the replacement: go through the shared resolver `resolve_device_by_identifiers(dev_reg, candidates, entry_id=...)` in `custom_components/googlefindmy/coordinator/helpers/registry.py`. It checks whether the registry offers the new method and calls `async_get_device` only where it does not; that check is a presence check per call, not a cached signature probe (the signature probe of this repository is `detect_device_registry_capabilities`, which answers a different question). **No call site may name `async_get_device`.** Since AP-16 there is none left in the production tree: the last one (`__init__.py::_async_relink_entities_for_entry.lookup_device`) went through the resolver, and the ratchet in `tests/test_guard_device_registry_kwargs.py` -- which is where the current number lives -- carries no `async_get_device` entry any more. It only ever shrinks, so a new entry there is a regression, not a starting point. Do not call the deprecated helper directly, and do not build the entry scoping by hand. **Superseded instruction, do not restore:** a call site may not re-add an identifier-only scan as a fallback either. The shape AP-16 removed searched by identifier alone, took the first match and only then checked ownership, discarding it -- which means a second device carrying the same identifier under *our* entry was never reached. Scoping the lookup is not a narrowing that costs a hit; it removes hits that were never valid answers and reaches ones the old shape could not. Background: `docs/AI_DEPRECATIONS_GUIDE.md`, section VI.
  * When choosing `use_name`, reuse a matching device entry on collisions; otherwise deterministically disambiguate the name (for example, suffixing with the subentry key or short identifier) and log the collision resolution at debug level.
  * Keep the debug log format stable so tests can assert the disambiguation path when multiple trackers share a hub.
* **Race-condition mitigation:** When programmatically creating subentries, immediately yield control back to the event loop (for example, `await asyncio.sleep(0)`) before invoking `hass.config_entries.async_setup(...)`. This prevents `homeassistant.config_entries.UnknownEntry` errors while the config-entry registry finalizes the new child entry. Leave a short inline comment describing the yield so future contributors retain the guard.
* **Paced discovery guardrails:** When throttling the lightweight device-list refresh, avoid advancing the pacing baseline while we are still retrying a transient empty response (`_EMPTY_LIST_QUORUM` backoff). Keep the cached list and allow the short retry to run before starting a new interval so recovery is not delayed by the long discovery cadence.
* **Empty platform setups:** If a platform can legitimately start without entities (for example, when tracker discovery returns no devices on a cold boot), still call `async_add_entities` once with an empty list right after listener registration. Home Assistant treats this as a successful setup, ensuring unloads succeed even when the integration never surfaces entities during initial discovery.
* **Tracker registry gating (canonical):** A newly discovered tracker is an entity, not an account: it is added silently through the `dynamic-devices` listener path and **never** opens a cloud discovery flow, so no card and no user click stand between the account's trackers and their entities. What remains of the former discovery gate is a registry check with a different outcome, and three properties are binding.
  * **After scheduling, never before.** Registry-aware gating belongs **after** entities are scheduled; use the coordinator's tracker registry helper (for example, `find_tracker_entity_entry`). Pre-scheduling probes double-count work without changing behavior.
  * **Judged after a grace period, not on the next callback.** `schedule_add_entities` hands back no awaitable, and a later coordinator notification is no synchronization barrier for the add task: a poll pushes per-device updates and then republishes its final snapshot, which for the last device can arrive back to back without yielding. Arm the probe with a wall-clock delay (`async_call_later`) instead, re-arm it on every further addition, and cancel it on unload. A probe that runs too early sees an entity Home Assistant has not registered *yet* and reloads a healthy entry.
  * **Outcome is one self-heal reload per entry, not a discovery flow.** When scheduled trackers are still missing from the registry once the grace period has passed, schedule a single reload, guarded by the domain-level one-shot latch (`claim_registry_selfheal_reload`) so a permanently empty registry cannot reload in a loop. Resolve the reload lever *before* claiming that latch, so an older core without `async_schedule_reload` does not burn the entry's only attempt. Ask `entry_reload_gate.entry_reload_is_hopeless` next, still *before* the one-shot claim and with the `ConfigEntry` this platform already holds (its hass double carries no entry manager, and the gate must not depend on one): the one-shot latch is released only in `async_remove_entry`, so an attempt spent on an entry that can never reach a setup is gone for that entry's life, while a disabled entry the user re-enables would still deserve its repair. Nothing is claimed at that point, so a hopeless verdict returns without handing anything back. Then claim the shared `claim_pending_entry_reload` latch as well, because the one-shot latch answers a different question ("has this entry healed itself yet") and knows nothing about a reload another owner already scheduled; when that shared claim fails, hand the one-shot back and stand down, so the entry's only attempt is not spent on someone else's reload. Re-polling the device list is deliberately not the lever here: the ids are already known, so no entity would be built a second time.
  * **The trackers that *did* register are promoted into the polling set.** `_enabled_poll_device_ids` is derived from the *entity* registry but rebuilt only on *device* registry events, and this coordinator subscribes to no entity-registry channel. A brand-new tracker gets its device-registry entry from `_ensure_registry_for_devices` **before** its entity exists, so the rebuild that entry triggers records it as present and not enabled -- and the polling predicate admits a device only while it is enabled or still absent from the registry. Without a second look the silently added tracker would be skipped from the next cycle on, entity and all, until a reload or a restart. The probe is the point where the addition is known to have landed, so it re-derives the sets there (`coordinator.reindex_poll_targets`). Independent of the missing-check, **not** of the count: with nothing registered the rebuild has no new input, and with something registered it runs even while the rest is still being repaired, because a self-heal reload can stand down and the trackers that did register must not wait for a reload that may never come. Note the asymmetry when changing this: dropping the count guard makes the probe rebuild on every fruitless run, dropping the independence from the missing-check strands every tracker that landed alongside one that did not.
  * This file is the single source of truth; the `tests/AGENTS.md` tracker section points back here to keep runtime and test expectations aligned.
* **One owner per entry reload:** Home Assistant's `async_schedule_reload` does not coalesce, and `async_reload` is an unload plus a setup either way, so two schedulers mean two consecutive teardowns. Every path that writes credential-relevant keys through `async_update_entry` also notifies the integration's update listener, which reloads the entry so those credentials take effect (that listener is why the options flow must not use a reloading base: Home Assistant deprecated pairing an update listener with the reloading config-flow methods in 2026.6 and turns it into an error in 2026.12, and for `OptionsFlowWithReload` it is a hard `ValueError` in `OptionsFlowManager.async_finish_flow` already today, raised *before* the options are written. `OptionsFlowBase` in `config_flow.py` is therefore the plain `OptionsFlow`, and every options step that needs a reload asks for one through `_schedule_claimed_reload`. Upstream's own preference is the other direction, dropping the listener; that is not open here while the listener also carries the live watch-path refresh). Any flow that additionally reloads the entry itself (the discovery fallback writer, the non-interactive discovery update, reconfigure, the options credential refresher) therefore claims `claim_pending_entry_reload` first and stands down when the claim fails. The **semantic-location**, **subentry-repair**, **device-visibility** and **settings** options steps belong to the same set, but reach the latch through `_schedule_claimed_reload` rather than by reloading themselves. Settings is the plainest of them: its options are read at setup time, it used to inherit a reload from the reloading base, and once that base was gone it had to ask for its own or take effect only after the next restart. Asking for its own means asking on the same condition the core used, not unconditionally: `OptionsFlowManager.async_finish_flow` scheduled on `async_update_entry(...) and automatic_reload`, and that call returns `False` for an unchanged payload, so confirming the form without an edit must claim nothing. One comparison is enough for that, because the step writes only the options payload, which is compared against `entry.options`. (A second comparison for a copy into the selected subentry went away with the feature-group selector, which had no account-level effect.) Visibility (`OptionsFlowHandler.async_step_visibility`) is the one with the hardest reason, and it is not symmetry with its siblings: un-ignoring a device reverses a removal Home Assistant already carried out, because `async_remove_config_entry_device` returned `True` for an ignored device and the registries dropped it. Putting the id back into the options does not undo that. The platform listeners do fire again on the next poll, but every platform guards on monotone per-setup known-sets that never lose an id (`device_tracker` alone keeps two, `known_ids` and `added_unique_ids`), so nothing is rebuilt. Only a reload starts those sets from empty, which is the same verdict the docstring of `_verify_pending_registry_entries` reaches for the self-heal probe. The claim sits inside the `if to_restore:` branch, so confirming the form without a selection stays inert. For all four of them the listener is not a competitor at all: it compares a `_credential_fingerprint` and reloads **only** when credential-relevant keys changed, so a purely option- or subentry-scoped write leaves it silent. The fingerprint covers every credential-relevant key in full, the receiver-owned `fcm_credentials` inside the secrets bundle included. A write by the FCM receiver itself is told apart from a user change by a one-shot digest receipt (`entry_self_write`): the receiver notes the digest of the value it is about to store, and the listener consumes it and skips the reload only when the rest of the fingerprint (`_credential_fingerprint_without_registration`) is unchanged and the stored member matches the receipt; every other change reloads once. Reason: excluding a member from the fingerprint also hides a user change of that member, so an imported `secrets.json` that differs only in `fcm_credentials` would take effect only after the next restart. Do not narrow the fingerprint to silence a writer; give the writer a receipt instead. Enforced by `tests/test_guard_credential_entry_writes.py` and `tests/test_fcm_entry_self_write_receipt.py`. Read the latch there as protection against the *grace-period probe*, not against the listener; mistaking the one for the other invites "the listener covers this anyway", which for those four steps is false. One more reload owner deliberately holds no latch: `services.py::async_rebuild_registry_service`. It runs on an explicit user action, no collision with it has been measured, and its lever would remain an awaited `async_reload` regardless. Named as a standing residual, not as something already handled: if a collision ever shows up, this is where to look first. That listener is not a guarantee, though: Home Assistant removes it when the entry is unloaded, which is the state expired credentials leave behind (`SETUP_ERROR` after `ConfigEntryAuthFailed`). A path that lets the core's unique-id guard perform the write with `reload_on_update=False` therefore has to schedule the reload itself as well, through the same latch, once it has established that the write landed; otherwise the credentials stay ineffective until a restart and the durability gate in `async_setup_entry` never consumes the staged bundle. The same holds for the background scheduler on the other side: the tracker registry self-heal claims it too, so a credential write and a grace-period probe cannot tear the same entry down twice. Claim **last**, immediately before scheduling, and release the latch where the reload arrives (unload, setup, entry removal). Release it **after** the unload has run, not at the head of `async_unload_entry`: the platform teardown is the longest stretch of a reload, and a latch released before it lets the schedulers that do not wait for `LOADED` (the credential-writing flows and the registry probe). They do consult `entry.state` by now, through `entry_reload_gate`, but only for the *terminal* states; `UNLOAD_IN_PROGRESS` is deliberately not one of them, so the reason for releasing late is unchanged claim it again and queue a second reload while the replacement setup -- which reads the newest `entry.data` anyway -- is already coming. A `finally` is the right place, so a failed unload and an unload that is not part of a reload hand the latch back too instead of keeping one they would never release. An update-listener invocation that Home Assistant queued before an unload still runs afterwards, so a listener that decides on captured state must check that it is still in `entry.update_listeners` before acting. A claim is a **promise to reload**, so every dead end has to hand it back. A path that reloads *directly* keeps the promise open for its task's whole lifetime, and that task can end without a reload (`async_unload` raises `OperationNotAllowed` for an entry in a non-recoverable state -- `FAILED_UNLOAD`, `MIGRATION_ERROR`, `SETUP_IN_PROGRESS`, `UNLOAD_IN_PROGRESS` -- the task is cancelled, or a deferred retry runs out of options). None of the release points fires then, so the latch would stay set for the life of the process and every later credential write would stand down with its credentials ineffective. Release on those dead ends -- releasing once too many only risks one reload too many, which is the direction this latch fails towards anyway. **The scheduled path is not exempt, only unobservable.** `_schedule_claimed_reload` releases the latch when the *synchronous* scheduling call raises, and that covers the reachable synchronous failures (`async_schedule_reload` resolves the entry and cancels its retry setup before it returns). The reload itself, though, runs in a core-owned task that `async_schedule_reload` neither returns nor exposes, so the very same `OperationNotAllowed` or cancellation ends that task with the latch still claimed and no callback to hand it back. Reachable, for example, after a failed unload: the `finally` above hands the latch back while the entry sits in `FAILED_UNLOAD`, and the next claimant schedules a reload that can only raise. **That residual is now closed in `_schedule_claimed_reload`** by `entry_reload_gate.entry_reload_is_hopeless`, a check that runs *before* the claim. Every claimant in the config flow runs it: that helper, the **non-interactive discovery update**, the **reconfigure** path, and the **options credential refresher**, which runs the same check before its own direct claim in `_finalize_success` and, where it fires, reports `credentials_saved_not_reloaded` instead of `reconfigure_successful` so the user is not told the new credentials already apply. It covers the tracker registry self-heal in `device_tracker.py` as well, which is why the check no longer lives in the config flow: `entry_reload_gate.entry_reload_is_hopeless` sits in a leaf module of the integration package, next to the latch and reachable from both sides without an import cycle, and `config_flow` imports it under its former private name. That probe needed it most, because it is the one claimant whose timer can outlive a failed unload: `async_on_unload` callbacks run only in the success branch of `ConfigEntry.async_unload`, so a failed unload leaves the entry in `FAILED_UNLOAD` **and** the grace timer armed (core `2026.2.3`). There the gate sits between the lever resolution and the one-shot claim, ahead of both latches, because the one-shot is handed back only on the two failure paths that took it themselves and in `async_remove_entry`; a hopeless verdict returns before any claim, so an attempt spent there would be spent for that entry's life, and putting the gate behind the one-shot would buy a third release path for no gain. The credential update listener does not need it: its `LOADED` check keeps it away from all three cases. Its shape matters: it is a **positive list of terminal states**, `MIGRATION_ERROR` and `FAILED_UNLOAD`, and explicitly **not** the negation of `entry.state.recoverable`. Home Assistant reports `recoverable is False` for four states, but the other two, `SETUP_IN_PROGRESS` and `UNLOAD_IN_PROGRESS`, are transient and heal on their own: `async_reload` enters `entry.setup_lock`, which the running lifecycle operation holds, so a reload scheduled during either one waits and then runs against a state that is recoverable again (the one path around that lock, the `entry.domain not in hass.config.components` short circuit, is closed because `setup.py` registers the domain before the setup). Standing down for a transient state would drop a legitimate reload together with the credentials that were just written -- the same damage this latch exists to prevent, with the sign flipped -- and the latch is free during `SETUP_IN_PROGRESS` anyway, because it is released at the head of `async_setup_entry`. Do not "simplify" the positive list into a `recoverable` check. An unknown future state is not on the list either and therefore keeps today's behaviour. Every core behaviour cited in this bullet was measured against `homeassistant` **2026.2.3**; a core bump puts the question again rather than inheriting the answer.

Two further cases are hopeless without being visible from the outside, and the check covers both: a **disabled** entry (`async_reload` returns right after the unload -- `if not unload_result or entry.disabled_by: return unload_result` -- and never calls `async_setup`) and an **ignored** one (`ConfigEntry.async_setup` bails out on `if self.source == SOURCE_IGNORE or self.disabled_by: return`). In both the state stays recoverable and the unload result is truthy, so neither the state nor the return value distinguishes them from a reload that landed. For the disabled entry the damage window ends when it is switched back on, because the setup that follows releases the latch at its head; for a terminal state no setup follows at all and the latch would stay claimed until the process restarts.

**The check narrows the window; it does not close it.** It reads the entry *before* the claim while the reload runs later in a core-owned task, so an entry can enter `FAILED_UNLOAD` in between, and it can equally be **disabled** in between: `async_set_disabled_by` sets the field before it calls `async_reload`, and the `_abort_reauth_flows` that runs there filters on `match_context={"source": SOURCE_REAUTH}` and therefore cancels no reconfigure flow. For the scheduled path this remainder is irreducible, because the core does not hand out the task. **Do not read this paragraph as full coverage.** Two paths reload *directly*: the non-interactive discovery update (`ConfigFlow.async_step_discovery_update_info`) and reconfigure (`ConfigFlow._async_reload_entry_after_reconfigure`). Both now run `entry_reload_gate.entry_reload_is_hopeless` **before** the claim, like `_schedule_claimed_reload` and the options credential refresher; the discovery fallback writer never needed its own, because it schedules through `_schedule_claimed_reload` (`ConfigFlow._async_write_entry_credentials`) and is covered there. Anchors here are symbol names on purpose: the three line numbers this paragraph carried before drifted by twelve lines within hours of being written.

What each direct path does with the *outcome* differs, and the difference is deliberate. The discovery update evaluates it: an exception or a cancellation hands the latch back through the `except BaseException` in `_reload_and_normalize`, and a falsy result is passed to `entry_reload_gate.falsy_reload_left_the_latch_behind`, which releases only where no release point ran. It schedules no retry, because the step ends in an abort anyway and the next setup reads `entry.data` afresh. Reconfigure does **not** release on falsy; it hands the reload to the core scheduler instead, and releases only when that hand-off is refused, nothing follows it, **and the same classifier says the latch can still be ours** (`_give_up_after_a_falsy_reload`). That last condition is not decoration: a falsy result means a failed unload or a failed setup in two of its shapes, and both of those released the latch at the `finally` of `async_unload_entry` respectively the head of `async_setup_entry`, so between that release and the refused hand-off another writer may have claimed it. Releasing then would discard *their* promise and let the next caller queue the second teardown this latch exists to prevent, and `discard_pending_entry_reload` cannot tell whose claim it drops. Its narrower `reload_result is False` test rather than a falsy test is likewise deliberate: it guards against a test double that returns `None`, which would make every successful reload look like a dead end. The **other** dead ends on that path -- exception, cancellation, a retry that could not be armed, a task handle that reports no outcome -- keep releasing unconditionally, on purpose: there no result exists, the post-reload state proves nothing, and a latch left behind would swallow every later reload of the entry for the life of the process.

The check before the claim does **not** catch a reload that returns a truthy result without ever reaching a setup, and two shapes do exactly that: a **disabled** entry (`async_reload` returns the unload result at `config_entries.py:2317` and never calls `async_setup`) and an **ignored** one (`ConfigEntry.async_setup` bails at `config_entries.py:667`). For an entry that is already unloaded, `ConfigEntry.async_unload` returns `True` at `config_entries.py:953` -- at `:949` for the ignored one -- without running our `async_unload_entry` at all, so neither the unload `finally` (the `finally` of `async_unload_entry`) nor the head of the setup (the head of `async_setup_entry`) fires and the claim stays behind. Reachable for reconfigure: an entry disabled while its form stands open, because `async_set_disabled_by` sets the field before it reloads (`config_entries.py:2335`) and the `_abort_reauth_flows` that runs there filters on `SOURCE_REAUTH` (`config_entries.py:3999`) and cancels no reconfigure flow. Named as a standing residual, and a bounded one: the latch is a per-entry set (`_ensure_pending_entry_reloads`), so a stranded claim blocks nothing but this entry, and for as long as the entry is disabled every other claimant either runs the hopeless check and stands down anyway or needs a loaded entry. It ends when the entry is switched back on, because the setup that follows releases the latch at its head, and when the entry is removed (`async_remove_entry`). The check *before* the claim narrows this window but does not close it, for the same reason as the paragraph above: it reads the entry before the claim while the reload runs after it. What it does close is the case where the entry is **already** hopeless when the flow arrives, and that is the common one, because a reconfigure is typically run against an entry that is not working. What remains is the entry that turns hopeless in between.

A check on the entry *after* a truthy reload would catch that remainder, and it is still **not** done here, deliberately. `discard_pending_entry_reload` knows no owner: it is a bare `set.discard` on a `set[str]` (`__init__.py`, `pending_entry_reloads`). After a truthy reload two situations are indistinguishable from inside this path: either our unload never ran and we still hold the claim, or our unload ran, released the latch at its `finally`, and another writer has claimed it since. Releasing in the second case would cause exactly the double reload this latch exists to prevent, which is the same hazard the falsy paths already guard against through `entry_reload_gate.falsy_reload_left_the_latch_behind` (`_release_claim_when_reload_fails`, the discovery update, and reconfigure's refused hand-off). The guard works there because a falsy *result* narrows which shapes are possible; after a **truthy** one it cannot, which is why the remainder survives. Closing it therefore needs a latch that knows *who* holds it (a claim token or generation counter), not another read of the entry. Until then the remainder is named, bounded and pinned, not silently carried.

Pinned by `test_reconfigure_stands_down_for_an_entry_that_is_already_hopeless` (the closed half) and `test_reconfigure_strands_the_latch_when_the_entry_is_disabled_in_flight` (the open half), so neither can change unnoticed. The second turns red as soon as the latch gains owner semantics, and this paragraph has to be corrected in the same change. Two direct paths now have **both**: the options credential refresher and the non-interactive discovery update. In each the check narrows the window before the claim and the result evaluation catches what falls through it, the refresher through a done callback on its task, the discovery update inline after its `await`. Reconfigure has **both** as well, with a different outcome: it delegates a falsy result instead of releasing, and where that delegation is refused it consults the same classifier before it releases. That callback reads the task's *result* as well as its exception, because `async_reload` reports a failed unload -- and a component it could not set up -- by returning `False` rather than by raising; a test double whose `async_reload` returns `None` therefore makes every successful reload look like a dead end and silently defeats the coalescing. A **disabled** entry is deliberately not covered by that result check: it returns the truthy unload result without reaching a setup, so only the check before the claim catches it. The registry self-heal named above now has the check but still no result to evaluate: `async_schedule_reload` returns nothing, so its share of this residual stays open in full.
* **Service-device fallback scan:** `_resolve_service_device` now includes a registry scan to detect legacy service identifiers when the primary identifiers are missing. Preserve this fallback when updating relink helpers so service sensors keep targeting the correct device across migrations.
* **Subentry-aware empty registrations:** For subentry platforms, schedule empty `async_add_entities`/`schedule_add_entities` callbacks only after confirming the forwarded `config_subentry_id` matches the one expected by the platform (for example, immediately after `ensure_config_subentry_id`). Skip registration entirely—and log a debug deferral—when Home Assistant forwards an unrelated `config_subentry_id`. When the subentry ID is correct but no entities are produced, register the empty callback immediately after listener setup so unload bookkeeping still completes.
* **Visibility metadata shapes:** Coordinators may expose `_subentry_metadata` entries either as mapping-like objects or attribute containers. Normalize `visible_device_ids` through helper functions before writing them back via `async_update_subentry` so both shapes remain compatible with strict mypy runs and runtime subentry managers.
  * **Log examples:**
    * Mismatch deferral: `Sensor setup skipped for unrelated subentry '<forwarded>' (expected one of: <known ids>)`.
    * Empty registration after listener: `Device tracker setup: subentry_key=<key>, config_subentry_id=<id>` (listener attached) followed by an empty `schedule_add_entities` call before returning.
  * Empty deferrals still need to report as a loaded platform: log the mismatch and call `schedule_add_entities` with an empty list so Home Assistant marks the forwarded subentry as initialized even when no entities apply.
* **Never-loaded platform cleanup:** Whenever a subentry platform unload path is skipped because the platform never loaded, invoke the purge helper that clears tracker entity and device registry links for that subentry before returning. This prevents stale entities from surviving reload attempts and keeps registry hygiene aligned with the teardown patterns above.
* **Thread-safe retry scheduling:** When retry callbacks are dispatched from worker threads or callbacks that may run off the event loop, enqueue the coroutine using `hass.add_job` if available (or `loop.call_soon_threadsafe(...)` as a fallback) instead of `hass.async_create_task`. This preserves Home Assistant’s thread-safety guarantees and keeps retry handles compatible with the shared scheduler helpers.
* **Background-task stub signatures:** The poll cycle is started with `config_entry.async_create_background_task(hass, target, name)` and, without a config entry, with `hass.async_create_background_task(target, name)` (`coordinator/polling.py`, `name=` passed as a keyword); both core signatures end in `eager_start: bool = True`, and the integration relies on that default instead of passing it. A test double for either method must accept these arguments and should return an `asyncio.Task` or `None`: the result is held as `_poll_cycle_task`, and the coordinator teardown calls `done()` on it and, while it is not done, `cancel()` and awaits it (`coordinator/main.py`). A return value without `done()` fails only at unload; a `MagicMock` passes silently, because its `done()` is truthy and the teardown skips it.
* **Allow-list growth for devices the account gained:** A subentry's stored `visible_device_ids` is a device-to-subentry **assignment**, not a user's show/hide choice. It now asks `_stores_visible` as well, so a present empty list survives this writer, while a group that never carried the key is still filled. **"Survives this writer" is the whole claim, and the narrowness is measured rather than modest:** the condition is applied to the tracker group alone, and that is the one group the unassigned-device merge feeds, so a stored empty list there does *not* end up as "shows nothing" -- the group is handed every device no other group owns, and `update_visible_device_ids` persists that as its new stored list (measured 2026-08-06: a lone emptied tracker beside a foreign group holding `device-3` comes back holding `device-1` and `device-2`). Emptying a *non*-tracker group does mean "shows nothing", end to end. Neither resolver's **scan** produces new residue. The qualifier is load-bearing: the flow resolver's hand-over branch above the scan is deliberately left unguarded, and it produces no residue today because it is unreachable (`async_get_supported_subentry_types` returns `{}` unconditionally, so core never registers these handlers, and `async_step_hub` passes no `subentry`), not because it is closed. Already stored residue is unaffected either way, which is what this paragraph is about. The stored subentry keeps them, and so does the folded group's own allow-list: only its claim to *own* those devices is suspended. Without that exemption the devices land in no group at all. Removing the ids from the in-memory copy outright would do both at once, and the second half is a defect rather than a shortcut: `allow_filter` reads an absent list as **no restriction**, not as no assignment, so a folded group that *wins* its core key was handed the entire device index, devices another group owns included, and the manager write-back made that durable (`::test_ap4_a_parked_tracker_that_wins_keeps_its_own_allow_list`). A synthesised group has nothing of its own to persist into, so it persists nothing; the metadata is still built, because the readers need a tracker group. (d) The base case: `_subentry_payload` stores the key only `if visible_device_ids`, so a group created without a selection never has one. For the tracker group that *is* the contract ("assigned to nobody belongs to the tracker"); for any other group it is the same fail-open reading. **(b) deserves its own note rather than the collective "changing it would move devices":** it is reachable through ordinary use, not only through migration residue. The repairs move writes `tuple(sorted(...))` back unconditionally, so moving the *last* device out of a group stores `()` for it -- and on the next refresh that group sees every device instead of none. That behaviour moved devices against the user's stated intent, which is why (b) has since been closed **in full**: a *present* key now normalises to a set even when nothing survives, so an empty or all-unusable list restricts to nothing instead of collapsing into "no restriction". An *absent* key still reads as unrestricted, and the two are deliberately not equated -- equating them would blind every freshly created group, which stores no key at all. The migration reasoning the earlier text was waiting for is the log line `_record_allow_list_reinterpretation` writes once per subentry per coordinator instance, which means a restart and a config-entry reload each re-emit it. It names the subentry and how many entries were stored, and deliberately neither the group key nor the stored values, because a legacy group key is an email address and the stored entries are namespaced device identifiers, both of which this repository forbids logging. The subentry id is what an operator needs to find the group again and reassign its devices; removing the key outright restores the old reading, though only until the next setup, which writes a derived list back. * **A definition is a partial description, so a sync must not delete by omission.** The core replaces `ConfigSubentry.data` wholesale, so any writer that builds a payload from a definition and hands it over as `data=` **deletes** every stored field the definition happens not to carry. Three sites in this integration write a subentry during setup and they fail in different ways, which is why they are listed separately rather than as one rule: treating them as one case is what produced two of them. The count is scoped to setup on purpose: a **fourth** site carries the same class outside it, `_BaseSubentryFlow._build_payload` reached through `async_step_user`, whose `_visible_device_ids` reads the stored value and normalises an empty list to nothing, after which `_build_subentry_payload` omits the key and `async_update_and_abort` replaces `data` wholesale. `HubSubentryFlowHandler` and `ServiceSubentryFlowHandler` override that accessor, `TrackerSubentryFlowHandler` does not, so the tracker flow is the reachable shape. It is dead today for the same reason the hand-over branch above is: `async_get_supported_subentry_types` returns `{}` unconditionally, so core never registers these handlers. Unreachable is not the same as closed, and it is named here rather than fixed because reaching it needs the flow-manager question settled first (`U-28`).
  * **`ConfigEntrySubEntryManager.async_sync` (`__init__.py`) deleted by wholesale replacement.** *Trigger:* every setup run, unconditionally, before the first refresh -- no user action, no precondition. `payload = dict(definition.data)` carries only what a definition names. Measured on 2026-08-06 against the production definitions, exactly two stored fields were lost that way, and the second had gone unnoticed: `visible_device_ids` and `feature_flags`. Closed by `_payload_preserving_stored_fields`, which widens the payload by the stored fields the definition does not govern. Two properties of that helper are load-bearing and were each reached by measurement: it is a **merge, not an allow-list of named keys** (an allow-list has to be extended whenever a writer stores a new field, and forgetting to extend it is the very failure being fixed), and it is computed **per target**, because the unique-id adoption path writes the payload onto a *different* subentry and a once-per-iteration merge would graft one group's stored fields onto another.   * **`ConfigFlow._async_sync_feature_subentries`, tracker branch (`config_flow.py`) lost a stored *empty* list, through two independent routes.** *Trigger:* a group whose stored list is present and empty -- reachable through ordinary use, since the repairs move stores `()` when the last device leaves a group. The residue's origin is not recoverable from the stored data, so a deliberate pre-`e8114585` move is cleared along with it; that is a carried cost of the invariant, named here rather than hidden. "Non-device" is decided on **both** axes wherever this exemption is applied, mirroring `config_flow._accepts_device_assignment`: the group key first (`NON_DEVICE_SUBENTRY_KEYS`), the subentry type second (`NON_DEVICE_SUBENTRY_TYPES`).

* **Two remainders of the managed-subentry index, named because the stale sweep's safety rests on them.** `ConfigEntrySubEntryManager.async_sync` guards its stale sweep with two barriers and both are narrower than they read. (a) The invariant that one `subentry_id` never sits under two managed keys is enforced in `_index_managed_subentry`, which conditions on the id's **truthiness** (`isinstance(subentry_id, str) and subentry_id`), while the sweep's own `desired_ids` set is built from an `isinstance(..., str)` test alone; an id that is the empty string therefore skips the invariant and still satisfies the barrier. The same truthiness gap sits one function away and was found by the same review rather than by this bullet: `_deduplicate_subentries` buckets by `isinstance(unique_id, str)` without truthiness, so two subentries carrying `unique_id=""` share one bucket although the empty string is not an identity, and its own sort key then treats that same value as *absent* in field 1; its `removal_targets.add(...)` likewise accepts an empty `subentry_id` where `async_remove` rejects one. That the rank stays gone is now enforced rather than described: `tests/test_subentry_manager_registry_resolution.py::test_select_canonical_ranks_no_subentry_type` freezes the tuple's field count and refuses any read of `subentry_type` or `LITERAL_CORE_KEY_OWNER` anywhere in `_sort_key`, because reinstating it changes no observable behaviour and therefore no behavioural test. Same reason for carrying them: no writer in `custom_components/` produces either value. (b) `update_visible_device_ids` assigns `self._managed_by_subentry_id[...] = key` directly in both branches of its own body (the async and the sync path) without moving the entry in `_managed`, so the reverse index can go stale; `_index_managed_subentry` then takes a wrong `existing_key` from it and never reaches its fallback scan, which runs only `if existing_key is None`, so the wrong key is popped and the real duplicate stays. ## Quick checklist (runtime patterns)

Use this list as a fast regression aid before or after changing runtime helpers:

* **Subentry hygiene:** Tracker healing must strip stray `config_subentry_id` links for the current entry, apply the correct tracker link, and log the removed IDs.
* **Hub naming:** Collect hub-linked device names before creating trackers, reuse matching entries on collisions, and deterministically disambiguate (with debug logs) when another hub device already owns the label.
* **Setup fan-out:** Forward parent platforms once via `_async_setup_new_subentries`, then dispatch subentry signals so platforms attach entities with the forwarded `config_subentry_id`.
* **Empty registrations:** When a platform has nothing to add (including subentry-aware cases), still register an empty entity list after listener setup so Home Assistant considers the platform initialized.

### Dispatcher pattern example (single forward + per-subentry signal)

Use this pattern to keep platform forwarding (once) separate from per-subentry entity creation:

```python
from homeassistant.helpers.dispatcher import async_dispatcher_connect, async_dispatcher_send


async def _async_setup_new_subentries(
    hass: HomeAssistant, parent_entry: ConfigEntry, subentries: Iterable[ConfigSubentry]
) -> None:
    platforms = {subentry.data.get("platform") for subentry in subentries}
    await hass.config_entries.async_forward_entry_setups(parent_entry, platforms)

    for subentry in subentries:
        async_dispatcher_send(
            hass, f"{DOMAIN}_subentry_setup_{parent_entry.entry_id}", subentry
        )


async def async_setup_entry(
    hass: HomeAssistant, entry: ConfigEntry, async_add_entities: AddEntitiesCallback
) -> None:
    seen: set[str] = set()

    async def async_add_subentry(subentry: ConfigSubentry) -> None:
        if subentry.subentry_id in seen:
            return
        seen.add(subentry.subentry_id)
        entities = build_entities_for_subentry(subentry)
        await async_add_entities(entities)

    for subentry in entry.runtime_data.subentry_manager.managed_subentries.values():
        await async_add_subentry(subentry)

    entry.async_on_unload(
        async_dispatcher_connect(
            hass, f"{DOMAIN}_subentry_setup_{entry.entry_id}", async_add_subentry
        )
    )
```

The forward call runs only once per platform set, while each subentry is delivered via dispatcher with its full context, aligning with the SSoT interface snapshot in [`docs/CONFIG_SUBENTRIES_HANDBOOK.md`](../../../docs/CONFIG_SUBENTRIES_HANDBOOK.md#quick-ssot-probe-per-subentry-platform-forwarding).

### Regression note

An earlier fix removed manual platform forwarding but missed programmatic subentry creation after startup, leaving late tracker groups uninitialized. The `_async_setup_new_subentries` helper (and accompanying regression tests) closes that gap by ensuring every new subentry is explicitly set up so Core can forward platforms with the correct `config_subentry_id`.
